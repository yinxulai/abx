# 运维规格（`operations/`）

**这一簇回答的是**：这台机器上它到底跑成什么样 —— 怎么验、验到了什么、
什么情况下会坏、坏了怎么读报错。

和隔壁两簇的分工：

| 簇 | 回答的问题 | 什么时候看 |
|---|---|---|
| [`../overview/`](../overview/) | 产品是什么、切成几块、边界在哪 | 改架构、评审设计 |
| [`../product/`](../product/) | 用户看到什么、每个状态说什么话 | 改界面、写文案 |
| **`operations/`（本文所在）** | **跑起来对不对、怎么证明、坏了怎么办** | 换机器、升级 docker、排查故障 |

判据很简单：**写「应该怎么样」的是设计，写「实测是什么样」的是运维。**
两边冲突时，运维这份以机器为准 —— 而且要把设计文档改过来（`overview/architecture.md` §19
就是这么攒出来的）。

## 这一簇的写法要求

三条，都是被真实事故逼出来的：

1. **只写有原始输出的结论。** 命令和它的真实回显一起贴，别只写「实测通过」。
   没有输出支撑的句子，要么补一次实测，要么标成「推断」。
2. **「没验」要单列一节。** 一份只说验过什么的文档，读起来像是全都验过了。
   [`docker-verification.md`](./docker-verification.md) §8 就是为此存在的。
3. **发现与设计文档不一致时，进专门的一节**，写清「文档怎么说 / 机器怎么做 /
   可复现的证据 / 影响 / 该改哪里、归谁」。散在正文里会被读漏。
