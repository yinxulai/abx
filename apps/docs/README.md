# @abx/docs

abx 的文档包。与 osw 同构：**`specs/` 是内部规格，`source/` 是面向使用者的文档**，两者不混。

| 目录 | 给谁看 | 进去吗 |
|---|---|---|
| [`specs/`](./specs/) | 实现者与评审者 | ❌ 内部规格，不进静态站 |
| [`source/`](./source/) | 使用者（未来的 zh / en 双语） | ✅ 进静态站 |
| [`assets/`](./assets/) | 文档引用的图 | — |

**为什么分两处**：内部规格要写「哪里会出错、什么还没验证、为什么这么取舍」，
使用者文档要写「怎么用」。把两者混在一起，结果是内部规格为了好看而丢掉最该写的东西。

入口：[`specs/README.md`](./specs/README.md)（文档地图）、[`roadmap.md`](./roadmap.md)（进度与验收）。

## 现状

**文档站本身尚未搭建。** 目前只有规格文档（Markdown），`dev` / `build` 是占位。
建站的时机：规格多到需要站点承载、或者 `source/` 下的使用者文档开写时。

建站时按 osw 的做法引 `@clarify-labs/cli`（osw 的 `apps/docs` 就是 Clarify 站点）。

## 加一篇文档

1. 判断它属于哪一簇 → 进 `specs/<簇>/`
2. 若不属任何现有簇，**新开一个目录**，并在 [`specs/README.md`](./specs/README.md) 的表里加一行
3. 一个主题只在**一份**文档里展开；其它地方提到它只写结论加链接

> 这条「一个主题只在一处展开」是 osw 的规矩，照抄：发现两处描述不一致时，
> 以权威文档和代码为准。
